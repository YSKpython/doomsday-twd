# The Transparency-Window Dilemma

Code and data for:

> Kılınç, Y. S. (2026). *The Transparency-Window Dilemma: Why the Doomsday
> Argument Cannot Settle Its Own Reference Class.*

The Doomsday Argument's 95% bound is fixed by the sum of two exponents — a prior
exponent `alpha` and an observation-window exponent `beta` — and the birth-rank
observation identifies only their sum. Two standard responses to the argument,
the Self-Indication Assumption and the absolute-transparency-window position,
turn out to sit on the same contour and to be observationally indistinguishable.

One command reproduces every number in the paper.

---

## Note for anyone who saw the earlier version

This repository previously accompanied a paper titled *Beyond Rank: An
Observation-Adjusted Framework for the Doomsday Argument*. That version has been
superseded and three of its central objects were **withdrawn**:

| Withdrawn | Why |
|---|---|
| Anthropic Tension Index `A = alpha*log10(k)` | base-10 surprisal under another name; it added nothing and is not used |
| window fraction `f = W/N_total` and the additive correction `A + log10(f)` | never derived, and it implies `P > 1` for small `f` |
| "growth potential" `lambda_gp` as a demographic parameter | `alpha` is the exponent of a **prior**, an epistemic input, not a property of the population trajectory |

The earlier claim that a Monte Carlo run "validated" the Doomsday Argument's
`U(0,1)` assumption was also wrong: `exp(-Exp(1)) ~ U(0,1)` is a
change-of-variable identity, provable in one line, and testing it confirms the
implementation and nothing else. `doomsday_checks.py` still runs that test, now
labelled for what it is.

The old scripts are kept unchanged under [`archive/`](archive/) so the record is
complete. They are not used by the paper.

## Quick start

```bash
pip install -r requirements.txt
python run_all.py
```

`run_all.py` finds the source files, converts each projection to an annual
`year,births` series, builds Tables 1 and 2, emits the coordinates plotted in
Figures 1 and 2, and runs the verification suite. It uses the interpreter that
launched it, so there is no shell syntax to get wrong — the same command works
in PowerShell, cmd and bash. If a step fails it stops and says which one.

To run the pieces separately:

```bash
python convert_wpp.py  data/raw/unpopulation_dataportal_20260725233543.csv --list
python convert_wpp.py  data/raw/unpopulation_dataportal_20260725233543.csv
python convert_ssp.py  data/raw/ssp_snapshot_1785016836.csv --variable "Female|Age 0-4" --no-midpoint
python doomsday_demography.py data/wpp2024_medium.csv --latex
python doomsday_checks.py
```

Every converter should report `years written: 75`. Anything else means that
script is on a different start year from the others.

## The model

```
prior        pi(N)      ~  N^-alpha            on [n_obs, N_max]
window       W(N)       ~  N^beta              beta = 1 proportional
                                               beta = 0 absolute
likelihood   P(n|N,O)   =  1/W(N)  ~  N^-beta
posterior               ~  N^-(alpha+beta)     on [n_obs, N_max]
```

With `sigma = alpha + beta` and `R = N_max/n_obs`, the doomsday tail is

```
P(N_total > k*n_obs)  =  (k^(1-sigma) - R^(1-sigma)) / (1 - R^(1-sigma))     sigma != 1
                      =  ln(R/k) / ln(R)                                     sigma  = 1
```

which tends to `k^-(sigma-1)` as `R -> inf` for `sigma > 1`. Carter is
`(alpha, beta) = (1, 1)`; the SIA from Jeffreys is `(0, 1)`; an absolute window
is `(1, 0)`.

## Layout

```
run_all.py                one command, reproduces everything
doomsday_core.py          shared math: tail(), posterior median, inverse-CDF sampler
doomsday_tables.py        Table 1 and its LaTeX body
doomsday_figures.py       Figures 1-2, and the coordinates embedded in the .tex
doomsday_demography.py    Table 2 from annual birth series
doomsday_checks.py        verification suite; each check labelled by what it proves
convert_wpp.py            UN Data Portal export  -> year,births
convert_ihme.py           IHME live births       -> year,births
convert_ssp.py            IIASA SSP population   -> reconstructed year,births
_common.py                shared validation used by the three converters
data/raw/                 the UN and IIASA source files as downloaded
data/                     derived year,births series (regenerated by run_all.py)
figures/                  rendered PNGs
archive/                  the withdrawn v1/v2 scripts, unchanged
```

The start year lives in one place: `START_YEAR` in `_common.py`, set to 2026 to
match the manuscript. Changing it means re-running every converter — a table
mixing start years is worse than either choice.

## Verification

`doomsday_checks.py` runs four checks and says what each one establishes, which
is not the same thing for all of them:

| Check | Kind | Result |
|---|---|---|
| Identifiability: the tail depends on `(alpha, beta)` only through their sum | substantive | max spread `0.000e+00` |
| One-unit shift: absolute window at `alpha` equals proportional window at `alpha-1` | substantive | max difference `0.000e+00` |
| Closed form vs an independent inverse-CDF sampler | implementation check | all `\|z\| < 2.1` at 2M draws |
| `exp(-Exp(1)) ~ U(0,1)` | implementation check only | a change-of-variable identity; no conclusion about the DA follows |

### UN WPP

The Data Portal export contains no `World` row, so the world total is the sum
over the 236 countries and areas it does contain. Those are all genuine
countries or areas — every `LocationId` is below 900, the UN's aggregate range —
so nothing is double-counted. `convert_wpp.py` checks this and drops any
aggregate it finds.

Two things differ between UN downloads and will silently corrupt the result if
you get them wrong. The Data Portal returns births in **persons**; the bulk WPP
"Demographic Indicators" files return **thousands**, for which you pass
`--scale 1000`. And the Data Portal labels the central projection `Median`,
while the WPP reports call it the *medium* variant; both spellings are accepted.
The script checks the implied mean annual birth rate against the world total of
about 1.3e8 and warns if it is implausible.

### IIASA SSP — the reconstruction is approximate

The SSP database publishes population by five-year age group and period, not
annual births. `convert_ssp.py` reconstructs a birth series from the 0–4 female
population, dividing by five and multiplying by `1 + 1.05` to convert female to
total births (105 male births per 100 female). It does **not** correct for
under-five mortality, so it undercounts: the SSP rows run 2.6–5.8% below the
matching UN WPP variant, which is the right sign and roughly the right size for
that omission. Each five-year average is assigned to the interval endpoint;
`--midpoint` uses the midpoint instead, which shifts `B_2100` by between −3% and
+1% depending on scenario. The script reports both. Table 2 of the paper states
all of this in its caption.

### IHME

The IHME Free-of-Charge Non-Commercial User Agreement permits publishing links
to IHME's download facilities but not providing downloads from your own hosting,
so the IHME file is not in this repository. To reproduce that row of Table 2:

1. Go to the GHDx entry for the GBD 2017 population and fertility forecasts
   (Vollset et al., *The Lancet* 396: 1285–1306) and accept the agreement.
2. Download the live-births file, `IHME_POP_2017_2100_LIVE_BIRTHS_*.CSV`.
3. Put it next to `run_all.py` and run it again. `convert_ihme.py` selects
   Global, Reference, counts, and writes `data/ihme2020_reference.csv`.

The total fertility rate file is not used; the live-births file is the direct
series.
